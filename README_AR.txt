صدى العراق — حزمة النشر

الإصدار التقني: 3.1
إصدار الواجهة: 3.1
معرّف البناء: SADA-3.1-DEPLOY-CACHE-BUILD-GUARD-PROVIDER-SYNC-20261028

متطلبات التشغيل
- Node.js 22 أو أحدث.
- تثبيت الاعتمادات عبر: npm install
- فحص المشروع عبر: npm test
- التحقق من تطابق الخادم والواجهة وملفات الإصدار عبر: npm run build
- ترقية رقم الإصدار للتحديث القادم: npm run release:bump (تتحول 3.9 إلى 4.0 تلقائياً)
- تشغيل الخادم عبر: npm start
- يجب نشر المشروع كخدمة Node.js، وليس كملفات ثابتة فقط.

إدارة قاعدة البيانات من لوحة الإدارة
1) افتح «قاعدة البيانات» داخل لوحة الإدارة.
2) أدخل رابط Firebase Realtime Database الخاص بمشروع صدى العراق.
3) اختر ملف Service Account JSON من Firebase Console > Project settings > Service accounts. يجب أن يكون الملف لمشروع sada-iraq-app.
4) احفظ الإعدادات، ثم أعد تشغيل خدمة الموقع من الاستضافة.
5) اضغط «اختبار اتصال Firebase الحقيقي» وتأكد من نجاح قراءة فعلية قبل استعادة أي نسخة.
6) أنشئ نسخة احتياطية من النظام الحالي قبل الدمج. استعادة النسخ تتطلب ملف نسخة صادرًا من صدى العراق وتأكيدًا صريحًا.

الأمان والتخزين
- ملف حساب الخدمة لا يُضمّن في الحزمة؛ عند حفظه من لوحة الإدارة، يُحفظ في مساحة بيانات الخادم بصلاحيات ملف خاصة ولا يُعاد عرضه إلى المتصفح.
- إعدادات الاتصال المحفوظة تُطبّق بعد إعادة تشغيل الخادم. عند استخدام الإعدادات المحفوظة، تصبح هي اتصال Firebase النشط حتى لو كانت هناك متغيرات قديمة في الاستضافة.
- اربط Railway Volume أو اضبط SADA_DATA_DIR إلى مجلد دائم؛ وإلا فقد تضيع ملفات الحساب الخاص والصور والبيانات المحلية عند إعادة النشر حسب نوع الاستضافة.
- لا ترفع ملف مفتاح الخدمة كأنه نسخة بيانات. مفتاح الخدمة صلاحية إدارية على قاعدة البيانات، فاحتفظ به سرًا ودوّره إذا سبق مشاركته.
- حساب الإدارة يبقى محفوظًا داخل admin-auth.json على هيئة scrypt password hash فقط، وليس كلمة مرور نصية. لا تنشر الملف أو المشروع في مستودع عام.
- النسخ الاحتياطية قد تتضمن بيانات شخصية، حسابات، طلبات وأرصدة وصورًا محلية؛ احفظها في مكان خاص.

النسخ الاحتياطي والاستعادة
- النسخة تضم بيانات Firebase، وملفات البيانات المحلية المحددة، وصور الوسائط المحلية المدارة من صدى العراق ضمن حد إجمالي قدره 24 ميغابايت للصور وحد 64 ميغابايت للنسخة كلها.
- إذا تجاوزت البيانات الحدود، يفشل إنشاء النسخة بدلاً من تنزيل ملف معروف أنه ناقص أو لا يمكن استعادته.
- الصور الموجودة على خدمات خارجية لا تُنزّل تلقائيًا؛ تُحفظ روابطها كما هي. الصور المحلية ضمن مجلدات custom-shop-media وmaintenance-media وpush-media تُضمّن وتُفحص بصمتها عند الاستعادة.
- الاستعادة عملية دمج محافظة: تضيف السجلات والحقول الناقصة، ولا تستبدل القيم الحية الموجودة مثل الأرصدة والطلبات. افحص الأعداد والحسابات بعد الدمج ولا تعتبر العملية استعادة مطابقة لكل القيم إذا كانت القاعدة الحالية تحتوي بيانات مختلفة.
- كلمات مرور المستخدمين تُضمّن فقط إذا كانت مجزّأة مسبقًا بصيغة مدعومة. لا تُصدّر كلمات المرور النصية أو مفاتيح المزودين أو رموز المصادقة.

بيانات الإدارة والتسجيل
- بريد المالك موجود في admin-auth.json، وتُحفظ كلمة مروره بصيغة scrypt hash؛ لا تُضمّن كلمة المرور كنص داخل الكود.
- تسجيل المستخدمين العاديين يبقى متاحًا عبر واجهة التسجيل، ويُحفظ الحساب في Firebase عند نجاح الكتابة والتحقق منها.

اختبارات التحقق
- npm test: اجتازت جميع اختبارات الإصدار الحالية، بما فيها تسجيل الدخول، إدارة الخدمات، استعلامات الطلبات، إعدادات قاعدة البيانات الخاصة، النسخ الاحتياطي/الاستعادة والتحقق من صور الوسائط في بيئة اختبار معزولة.
- نجاح الاختبارات المحلية لا يعني أن الاتصال بقاعدة Firebase الحية قد تم اختباره؛ نفّذ اختبار الاتصال من لوحة الإدارة بعد النشر.


نشر Netlify
- راجع NETLIFY_SETUP_AR.md. يجب نشر المشروع عبر Git متصل بـ Netlify أو Netlify CLI كي تُبنى Netlify Functions؛ رفع ملفات الواجهة وحدها لا يشغّل API.
- على Netlify استخدم متغيرات البيئة السرية FIREBASE_DATABASE_URL وFIREBASE_SERVICE_ACCOUNT_JSON وSESSION_SECRET. لا تضمّن مفتاح حساب الخدمة في ZIP أو ملفات الموقع.
- تخزين ملفات Function مؤقت؛ الصور والبيانات التي لا تحفظ في Firebase أو تخزين دائم آخر قد لا تبقى بعد إعادة التشغيل.

نشر Railway — إصلاح أمر البناء (مهم)
- ملف railway.json يحدد Railpack وأمر البناء `npm run build` وأمر التشغيل `npm start`؛ أمر البناء يشغّل كامل الاختبارات تلقائياً قبل قبول النشر.
- أمر البناء والتحضير قبل التشغيل يتحققان من تطابق معرّف الإصدار بين server.js وindex.html وpublic/index.html وconfig.json وملفات الإصدار.
- افتح `/api/release` بعد النشر؛ يجب أن ترى `version: 3.1` و`deploymentConsistent: true`.
- أمر البناء في package.json يفحص صياغة server.js فقط، ولا يعتمد على scripts/prepare-netlify.js؛ لذلك لا يتكرر خطأ MODULE_NOT_FOUND الخاص بسكربت Netlify أثناء بناء Railway.
- إعداد Netlify منفصل في netlify.toml ويستخدم scripts/prepare-netlify.js الخاص به.
- بعد رفع هذه النسخة إلى نفس مستودع GitHub والفرع المرتبط بخدمة Railway، تأكد أن package.json وrailway.json في جذر المستودع هما النسخة الجديدة. إذا كان Root Directory في Railway يشير إلى مجلد آخر، اجعله جذر المجلد الذي يحتوي package.json وserver.js وrailway.json.
- إعدادات الخدمة اليدوية في لوحة Railway قد تؤثر إذا كان إعداد Config File غير محدد أو يشير إلى ملف آخر؛ راجع Build Command وRoot Directory إذا استمر استخدام الأمر القديم.
